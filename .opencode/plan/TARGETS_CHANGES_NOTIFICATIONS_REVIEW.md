# Targets, Changes, and notifications review

Reviewed Reconner at `0f8a906`. This follow-up builds on the [Changes and scan scope audit](CHANGES_AND_SCOPE_AUDIT.md).

## Findings and the bell

1. **High · Bell filters fail for admin users.** The list query starts with an empty scope for admins. Selecting Deep, Watch, or Findings appends `AND n.type IN (…)` without a `WHERE`, resulting in an HTTP 500. The menu swallows the error, so the previous list and unread count can remain under the newly selected label. See [notification list query](../internal/api/notification_handlers.go#L71) and [bell request handling](../frontend/src/components/layout/TopBar.tsx#L132).
2. **High · Verified findings have no dependable bell alert.** The `new_vuln_finding` handler resolves a finding and sends it to the Telegram notifier. It writes no bell row, and the bell has no finding-event subscription. The Findings bucket reads pre-existing notification rows, so its existence does not guarantee that a newly verified finding will show up. The deep scan summary gives a cumulative verified total and cannot tell the operator which finding is new. See [finding delivery](../internal/scheduler/scheduler.go#L404), [scan summary](../internal/scheduler/scheduler.go#L3495), and [bell subscriptions](../frontend/src/components/layout/TopBar.tsx#L147).
3. **Medium · A filtered bell hides unread alerts and can clear them in bulk.** The badge is calculated for whichever category was last selected, including after the dropdown closes. **Mark all read** sends no category and marks every accessible notification, even findings outside the current view. The menu also marks everything locally if the write fails. Its API returns the newest 100 rows and has no way to reach older unread rows from the menu. See [badge and list queries](../internal/api/notification_handlers.go#L96), [mark-all API](../internal/api/notification_handlers.go#L163), and [bell action](../frontend/src/components/layout/TopBar.tsx#L173).
4. **Medium · Bell alerts open the target's default tab.** A scope change, status transition, and finding all open the base target route, leaving the operator to locate the event. The bell files watch-generated `new_host` alerts under Deep. Bell responses omit discovery metadata, so the new-host list stored by deep enumeration is unavailable to the dropdown. See [bell navigation](../frontend/src/lib/notifications.ts#L24), [bell type mapping](../internal/api/notification_handlers.go#L27), and [response fields](../internal/api/notification_handlers.go#L96).
5. **Medium · Bell and Changes read states disagree.** Notification rows surfaced in Changes use `change_seen`, while the bell uses `notification_reads`. Reading one copy leaves the other unread. Separately, an older globally read row can become unread for another user once the first user adds a per-user receipt, because that receipt disables the legacy fallback for everyone. See [Changes receipt](../internal/api/changes_handlers.go#L370) and [bell receipt expression](../internal/api/notification_handlers.go#L74).

## Telegram alert volume and coverage

6. **High · Turning off lifecycle messages needs to preserve the finding sweep.** New chats default to deep scan start, every phase, and finish. The phase and finish callbacks also sweep for verified findings from sources that lack live events. Switching off those message categories suppresses the messages and leaves the sweeps running today. Removing the callbacks during cleanup would also remove that coverage. See [chat defaults](../internal/api/telegram_bot.go#L325), [phase and finish callbacks](../internal/api/telegram_bot.go#L663), and [finding sweep](../internal/api/telegram_bot.go#L763).
7. **High · An older candidate can become a finding without a Telegram alert.** The verifier can update a saved row from candidate to finding without a corresponding live event or new creation timestamp. The native finding sweep filters by `created_at` inside the current scan window, so an older row promoted by that path can fall outside both notification routes. See [finding status update](../internal/scanner/verify.go#L620) and [Telegram sweep criteria](../internal/api/telegram_bot.go#L773).
8. **High · A verification result can label unrelated findings as verified.** The Nuclei verdict update uses the project and matched URL, so multiple templates at one URL can inherit a verdict from a single check. Telegram's sweep trusts that verification flag and timestamp, which can send extra alerts labeled verified or suppress the genuine row after a different verdict. See [verdict write](../internal/scanner/verify.go#L348), [update predicate](../internal/scanner/verify.go#L419), and [Telegram selection](../internal/api/telegram_bot.go#L775).
9. **Medium · Telegram controls do not match the signals they imply.** **New scope** controls the `scope_landed` message, which has no active caller. Upstream program additions, modifications, and removals use **Monitoring** and are sent only for favorited programs. **New hosts** controls the breadth emitter, while deep enumeration writes a bell row without the corresponding Telegram event. **Monitoring** combines genuine HTTP status changes with title, body, script, and other drift. Preferences apply to an entire chat with no project-level routing. See [chat toggle definitions](../frontend/src/components/system/TelegramIntegration.tsx#L192), [program scope bridge](../internal/scheduler/scheduler.go#L2794), [deep host discovery](../internal/scanner/subdomain.go#L312), and [outbox routing](../internal/api/telegram_bot.go#L631).
10. **Medium · Status messages lack the old code and can repeat the wrong row.** The Telegram bridge re-queries the latest notification by project and type, with second-resolution ordering and no event identifier. It passes an empty old value and uses the bell body as the new value. Multiple same-type changes in a burst can be mislabeled or repeated, and every call gets a fresh timestamp-based key. See [monitor event broadcast](../internal/scanner/monitor.go#L635), [Telegram bridge](../internal/scheduler/scheduler.go#L391), and [message formatting](../internal/api/telegram_bot.go#L697).
11. **Medium · Muting a category can leave old messages on the way.** The category is checked when inserting into the outbox. Delivery only checks whether the chat is enabled, so pending and retried phase messages can still send after the phase toggle is turned off. The queue also orders routine messages and findings by the same creation time, so a backlog of routine activity can delay findings. See [outbox delivery](../internal/api/telegram_bot.go#L580) and [queue preferences](../internal/api/telegram_bot.go#L631).

## Targets and project Changes

12. **High · Bulk actions can include targets hidden by the coverage filter.** Changing from All to Deep or Breadth filters the cards without clearing or restricting the existing selection. Delete and Set coverage still submit the full selection. The delete confirmation prints the count without identifying the projects, so a hidden target can be included without the operator seeing its name. See [coverage filter](../frontend/src/pages/Targets.tsx#L82), [bulk actions](../frontend/src/pages/Targets.tsx#L103), and [delete confirmation](../frontend/src/pages/Targets.tsx#L644).
13. **Medium · Project cards misrepresent watch recency and findings.** A healthy breadth-only project can show “Never scanned” because the card and the sort use `last_scan_at`, which the scheduler reserves for deep scans. The cards also sort by a lifetime count labeled Findings. That number excludes low and info native findings and includes non-rejected Nuclei templates that can still be unverified. The list offers no view of projects with recent findings or changes. See [project sorting](../frontend/src/pages/Targets.tsx#L283), [card labels](../frontend/src/pages/Targets.tsx#L470), [scheduler timestamps](../internal/scheduler/scheduler.go#L2465), and [finding count](../internal/scheduler/scheduler.go#L3107).
14. **Medium · Changing tabs quickly can put the wrong results on screen.** Target detail uses one shared result array. Switching clears the array, but earlier requests and delayed refreshes can still finish and replace it with rows from another tab or target. Each Changes refresh walks all API pages before drawing its first page, making this race easier to encounter on busy projects. A failed request also renders as empty data. See [delayed refresh](../frontend/src/pages/TargetDetail.tsx#L645), [tab fetch and state update](../frontend/src/pages/TargetDetail.tsx#L769), and [pagination helper](../frontend/src/lib/api.ts#L42).
15. **Medium · Project Changes loses chronology across hosts.** Identical type and before/after values form one group across all history, with a single representative URL and timestamp. Two hosts making the same transition on different days appear as one row until expanded. Repeated occurrences at one host are also collapsed across time. See [group key](../frontend/src/components/changes/changesModel.ts#L125) and [target table](../frontend/src/pages/TargetDetail.tsx#L1847).
16. **Medium · The program scope review panel can lag behind the Changes feed.** Target detail loads review events when the project ID changes. The live scope-change listener reloads the Changes tab when it is open, but does not refresh the separate approvals panel. A new event can appear in Changes while its review action is absent until reloading the page. See [initial data load](../frontend/src/pages/TargetDetail.tsx#L508), [live refresh](../frontend/src/pages/TargetDetail.tsx#L645), and [scope review actions](../frontend/src/pages/TargetDetail.tsx#L1014).

## Proposed daily view

| Surface | Default behavior |
| --- | --- |
| **Targets** | Show the latest meaningful activity, recent verified findings, and the next watch run or paused state. Keep watch and deep timestamps labeled. Link directly to a project's Changes and Findings. |
| **Global and project Changes** | Use the same timeline and filters, with the project fixed on its own tab. Lead with status transitions (`200 → 403`), new host names, and program scope additions, modifications, and removals. Show which field changed and whether scope approval is pending. Keep script, body, header, and technology diffs accessible through filters. |
| **Bell** | Show verified findings and meaningful project changes. Group bulk host and scope updates by project and round or sync, link to their detail, and retain unread findings when a filter is active. |
| **Telegram** | Default to verified findings, new hosts, upstream scope changes, and actual status transitions. Batch bursts by project and include a short count and a detail link. Keep routine scan starts, phases, and successful finishes in Scan activity. Keep finding delivery enabled at every severity and independent of lifecycle message settings. |

## Verification

In-memory SQLite fixtures reproduced the admin bell query failure, the legacy unread regression, delivery selection for a muted pending category, and the same-URL verification update affecting more than one record. An isolated Node check using the existing grouping function confirmed that separate URLs and dates collapse into one target Changes group. The focused Go suite stopped during setup because dependencies were missing from the local read-only module cache. Other findings were traced through the source.
