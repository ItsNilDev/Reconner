# Reconner scan data and Changes implementation plan

Implement this plan in the Reconner checkout. It describes the remaining issues reviewed at `5f13f41`, after the partial fixes in `6c5cdf6`. Compare the named code paths with the current branch before editing. Work through the steps in order and use the acceptance cases to verify the result.

## Expected result

- **Project Changes** has the same controls and layout on breadth and deep projects. **Sidebar Changes** uses that same component across projects. Both show real HTTP status transitions, new hosts, and upstream program scope changes by default.
- Each valid HTTP observation can update inventory and produce a durable change. Large projects, partially failed rounds, write failures, and coverage switches preserve the correct history.
- The UI identifies upstream scope edits and Watch scope landings by their actual event types. Current eligibility controls whether a historical Watch scope host can be promoted to a deep seed.
- The bell and Telegram focus on verified findings, new hosts, upstream scope changes, and real HTTP status transitions. Preserve existing findings delivery at every severity for enabled subscriptions. Keep routine scan activity available in Scan activity.

The current project route is `/targets/:id`. Both tiers already use the `monitor` tab inside `frontend/src/pages/TargetDetail.tsx`. That tab still renders the older table and loads the full per-target history through `changes.forTarget(id)`. The sidebar at `/changes` renders cards and filters through `frontend/src/components/changes/ChangeLog.tsx`. Use the sidebar component for the project tab as well, with its target fixed by the route. The coverage badges and the breadth round controls serve different purposes. Label them accordingly.

Keep this work focused on authorization, existing observation data, alert delivery, and presentation. Preserve the current scan phases and request budgets. Use SQLite fixtures, a fake tool executor, and loopback HTTP fixtures for testing.

## 1. Apply current scope before a task sends requests

Start in `internal/scheduler/scheduler.go`, `internal/scanner/scan_options.go`, `internal/scanner/exclude.go`, `internal/scanner/http.go`, and `internal/scanner/utils.go`.

1. Load effective scope from approved project assets, current linked program eligibility, and operator exclusions when the task starts. Apply it to breadth, deep, and per-asset runs. Keep the legacy `targets.domain` fallback for genuinely unmanaged projects. An empty managed scope produces a clear no-eligible-assets result. An error reading scope blocks the task with a visible error. `LoadExclusions` and the strict scope lookup currently let read failures become permissive defaults. Carry errors to the task outcome.
2. For linked projects, keep project asset selection and program eligibility as separate checks. Apply both. An exact program host covers that host. A `*.example.test` program rule covers descendants, with a separate rule needed for the apex. Respect configured port and path restrictions wherever they apply. A positive rule cannot override an applicable deny. Keep wildcard patterns as scope records. Filter literal patterns out of host input, host events, and inventory.
3. Revalidate a queued per-asset `scope_override` at execution time before creating endpoint seeds or invoking modules. Check the selected asset is still present and approved and is still eligible under the effective scope. Keep a previously excluded or revoked service visible as history while preventing further requests to it.
4. Pass the task context into native HTTP fallback requests. Apply the same destination checks before the first request and to each redirect. Reuse available scope and exclusion helpers. Keep host, port, and CIDR checks effective for the actual connection destination. Skip an input when its constraints cannot be enforced by the request path.
5. Gate **Promote to Deep seed** on current eligibility. In `internal/api/watch_coverage.go`, check the current asset status, its linked program eligibility, and applicable exclusions before updating its type. Apply the same validation to landed or promoted Watch assets in `loadProjectWebSeeds` and queued task admission. Preserve their history when eligibility is lost. Reconcile the `out_of_scope` marker from current policy when a valid grant returns. Report a conflict when current scope disallows promotion, and disable the action when eligibility is unknown.

**Verify.** A queued asset that loses approval is blocked before I/O. A scope lookup failure sends zero requests. A previously stored excluded URL stays visible as history and receives zero requests from either tier or native fallback. Cover exact versus wildcard program rules and a scope-limited redirect with fixture destinations. A revoked historical watch asset fails promotion and produces no deep seed.

## 2. Record HTTP changes from each committed observation

Start in `internal/scanner/http.go`, `internal/scanner/monitor.go`, `internal/scheduler/watch_changes.go`, `internal/scheduler/scheduler.go`, and `internal/database/migrations.go`.

### Compare equivalent observations

- Keep `http_services` as the latest inventory. Add a separate persisted comparison baseline keyed by project, normalized service URL, and observation type. Preserve scheme, effective port, and endpoint path or query when they identify a distinct service. Use explicit observation types for breadth HTTP, deep HTTP, and the monitoring path where request behavior differs. A native response can share a baseline only when its request and redirect behavior match that baseline. `probe_tier` on the shared inventory row is insufficient as the only baseline because each scan can overwrite it.
- A first valid sample for a comparison key establishes a baseline. Treat legacy status `0`, absent codes, and codes outside `100–599` as unknown. A valid, different code on a later comparable sample creates a `status_change` event. Equal codes with a changed title or body remain detail changes. Preserve the monitor’s existing confirmation when processing its observations. Keep structured `old_status` and `new_status` on status events.
- Seed a new baseline from existing data only where the old observation’s provenance is reliable. For mixed or unknown provenance, use the first new observation as the baseline. A breadth `302` and a deep `200` for the same stable redirect must establish independent baselines without an alert.

### Write the event with the observation

- Replace the breadth status diff over two alphabetically capped snapshots with a per-observation comparison. Pass the actual `task_id` from task execution into the writer. Write breadth events to `watch_round_changes` and deep events to `monitoring_changes`. Preserve watch title, technology, and redirect detail, which are currently produced by the snapshot diff. Compare those fields for actual observed rows. Remove the old status writer once the replacement is wired, so one response cannot create both versions of the event.
- Within one SQLite transaction, read the prior baseline, write any events, and update the baseline and service. Publish committed events by their existing durable ID after commit. If an event write fails, return the error and leave the comparison baseline available for retry. Handle concurrent writes without generating two events for one change. An unchanged repeat observation emits nothing. A later real recurrence must still emit a fresh event.
- Validate the observation has an admitted service URL and a valid code before saving it as a successful probe. Keep valid observations and their events from a phase that later fails. Preserve the failed phase result and avoid advancing liveness misses for unconfirmed work. Missing tools, corrupt output, and a clean successful round with zero responses must remain distinguishable. A phase with zero eligible inputs reports skipped or no eligible inputs.
- Use the same success path for host liveness in both the normal probe and native fallback. Link the service to the corresponding host and update alive status for a committed valid result. Preserve `http_services.source` for original provenance. Persist `probe_tier` at the successful write. In the HTTP results API and existing observed-service readers, include a seed once it has a valid observed code and recorded probe tier. Keep status-zero seeds out of the observed results. Review `internal/api/finding_handlers.go` and both `storeHTTPService` and `storeBasicService`.
- Link a bell entry to the durable event ID. Keep bell and Telegram delivery retryable from the committed event when enqueue fails. A notification error must be visible without making the comparison baseline advance independently of its event. Preserve the older branch’s data and read actual numeric columns where available.

**Verify.** A changed URL sorted after the first 5,000 services appears in its breadth round. A valid response followed by a tool failure saves the transition exactly once and leaves the phase failed. Two different tiers observing `302` and `200` on a stable redirect do not produce a transition. A first `0 → 200` creates inventory without an alert. Force the event insert to fail and confirm the baseline can still report `200 → 403` on retry. With a native fixture response, both the HTTP and Hosts views reflect the result. Probe an existing endpoint seed and confirm it becomes visible in the HTTP API while untouched seeds remain hidden.
